# Household Membership Implementation Design

## Goal

Implement the approved household membership and invitation contract so accounts can safely create and join multiple households, manage owner/member roles, and scope shared API access to current membership.

## Relationship To Product Contract

This design implements [`docs/product/contracts/household-membership.md`](../../product/contracts/household-membership.md). That contract is the client-facing behavioral/API source. This document records implementation structure, migration strategy, and security decisions. If an implementation detail conflicts with the product contract, update and re-approve the contract before coding.

## Current Context

- NestJS 12, PostgreSQL, and Prisma 7 are used by the API.
- `User` currently has one nullable `householdId`; the target allows multiple household memberships.
- `Household` currently uses an integer primary key and has no public opaque identifier.
- Household endpoints currently provide only a placeholder create operation.
- JWT authentication supplies a user identity to protected endpoints.
- Existing database migrations are in `prisma/migrations`; migration history must remain intact.

## Selected Architecture

Add focused household, membership, and invitation services/repositories behind a `HouseholdsModule`. Persist `HouseholdMembership` as the join entity between users and households, with a role and membership lifecycle timestamps. Persist invitations separately with a cryptographically random token hash, creator, expiry, and acceptance/revocation metadata. Add a unique UUID public ID for households and use it in the client API while retaining the integer database primary key internally.

Use household-scoped REST routes for current membership operations. Centralize membership/role checks in a household authorization service so every route checks access server-side. Use database transactions for membership/role/owner invariants and invitation acceptance, with unique constraints as the final defense against concurrent duplicate membership or token use.

Keep DTO validation, domain rules, and Prisma persistence separate. Controllers validate/translate inputs and outputs; services own business invariants; focused persistence operations own Prisma access. Use explicit request/response DTOs and typed domain errors instead of passing generated Prisma records directly through the API.

## Data Model And Migration

### Household

- Preserve the integer primary key and all existing relations during migration.
- Add a required unique public UUID generated by the database or application on creation.
- Continue to return the public UUID as the API `id`; never expose or require sequential database IDs in client paths.

### HouseholdMembership

- Fields: integer internal ID, user ID, household ID, role (`OWNER` or `MEMBER`), joined timestamp, and nullable left timestamp.
- Unique constraint for `(userId, householdId)` so an account has at most one membership row per household; rejoining reactivates the existing row rather than creating duplicates.
- Index household ID and user ID for authorization and list queries.
- Current membership means `leftAt IS NULL`.
- Preserve former membership rows for audit/context and historical attribution.

### HouseholdInvitation

- Fields: integer internal ID, household ID, creator user ID, unique token hash, created timestamp, expiry timestamp, and nullable accepted/revoked timestamps plus accepted user ID.
- The raw token is never stored. Generate at least 32 cryptographically random bytes and encode with base64url; hash with SHA-256 before persistence. Because entropy is high and generated server-side, a fast cryptographic hash is appropriate; rate-limit preview and acceptance endpoints.
- Invitation status is derived in this precedence order: revoked, accepted, expired (`now >= expiresAt`), otherwise pending.
- Only pending invitations are listed to household owners; the list exposes IDs, timestamps, and status, never token hash or raw token.

### Existing Data Migration

Use an expand/backfill/contract sequence:

1. Add household public IDs and the new membership/invitation tables without removing `User.householdId`.
2. Backfill one membership for every user with a non-null `householdId`.
3. Assign owner to the earliest-created existing user in each household; assign `MEMBER` to the others. Break equal-createdAt ties deterministically by ascending user ID.
4. Verify there are no legacy links missing a membership and every existing household with members has at least one owner.
5. Update application reads/writes to use memberships.
6. After validation and successful deployment, remove `User.householdId` and its old relation in a later migration. Do not combine destructive column removal with the first backfill migration.

Households with no existing users remain valid and can be used once an owner creates a membership through the normal creation flow. Migration must not delete household, address, task, or responsibility rows.

## API And Service Boundaries

- `HouseholdsController` exposes household creation, current-user household list, household details, and current member list.
- `HouseholdMembershipController` exposes role changes and membership deletion under `/households/{householdId}/members/{membershipId}`. The caller deletes their own membership to leave; an owner may delete another member's membership.
- `HouseholdInvitationsController` exposes owner-only pending list/create/revoke and public preview under `/invitation-previews`.
- Authenticated invitation acceptance creates a membership through `POST /household-memberships` with the invitation token in the body.
- `HouseholdService` owns household create/list/read operations and membership-scoped retrieval.
- `HouseholdMembershipService` owns membership authorization, role updates, removal, leave, reactivation, and last-owner rules.
- `HouseholdInvitationService` owns token generation/hash verification, expiry/status, creation/list/revoke/preview/accept flows.
- A focused `HouseholdAccessService` (or equivalent small provider) owns current-membership and owner checks and returns the authorized membership context to downstream operations.
- Controllers translate stable domain errors into the agreed error envelope and HTTP status; no controller directly queries Prisma.

Register JWT protection globally or on all protected controller routes while explicitly marking only invitation preview and pre-existing public auth routes public. Every service query involving household data must include the authorized public household ID/current membership condition; do not fetch by ID first and rely on client-side filtering.

### Route Set

- `POST /households`
- `GET /households`
- `GET /households/{householdId}`
- `GET /households/{householdId}/members`
- `PATCH /households/{householdId}/members/{membershipId}`
- `DELETE /households/{householdId}/members/{membershipId}` (owner removal or self-leave)
- `GET /households/{householdId}/invitations`
- `POST /households/{householdId}/invitations`
- `DELETE /households/{householdId}/invitations/{invitationId}`
- `POST /invitation-previews`
- `POST /household-memberships` (accept invitation)

Use stable opaque public IDs as route parameters. `CLIENT_APP_URL` is required when creating invitation links; validate it as an absolute HTTP(S) URL and configure production separately from local development. Build invite links using the configured `/invite` route and token fragment. Fail invitation creation with a configuration error if the base URL is missing/invalid; do not construct links from the incoming request host.

## Authorization And Transactional Invariants

- All household data operations require current membership except household creation and invitation preview.
- Owners alone can list/create/revoke invites, change roles, and remove other members.
- Any authenticated account can preview; only authenticated accounts can accept.
- Invite acceptance never grants owner role.
- Acceptance transaction checks invitation pending/unexpired, checks membership, creates/reactivates membership as `MEMBER`, and marks the invitation accepted for that user atomically.
- For concurrent acceptance, unique constraints and transaction conflict handling must ensure one accepting account consumes an invitation. If a second request from the same account races, return its existing membership; a different account receives `INVITATION_ALREADY_USED`.
- Role changes/removals/leaves use a transaction that prevents the current operation from reducing owner count below one. On a concurrent owner mutation conflict, return `LAST_OWNER_REQUIRED` and preserve the existing owner.
- Owners may remove/demote other owners if at least one owner remains afterwards.
- A user may leave a household. If they are the final owner, return `OWNER_TRANSFER_REQUIRED`.
- Role-changing an inactive member or removing a non-member returns `MEMBER_NOT_ACTIVE` without revealing membership in another household.
- Removing/leaving sets `leftAt`, revoking access immediately while retaining membership identity for historical attribution.

## Error Contract

Return JSON errors with `{ "code": "...", "message": "..." }`. Implement the codes/statuses in the product contract: validation 400, authentication 401, owner/last-owner authorization 403, non-visible household/member not found 404, invitation and owner invariant conflicts 409, and rate limit 429. Unknown/malformed invitation tokens should use a generic `INVITATION_NOT_FOUND` response; do not reveal whether a token was nearly valid. Expired/revoked/used states may be distinguished only after resolving an authentic token record.

## Testing

- Unit tests for public ID creation, owner/member policy, last-owner invariant, invitation status precedence, token hashing/validation, and membership reactivation.
- Controller/service tests for household creation/list/read and role-protected endpoints.
- PostgreSQL-backed integration tests for invitation acceptance transactionality, concurrent use, unique membership, migration backfill/tie-breaking, and owner-count invariants.
- Authorization tests verify a non-member cannot read a household/member/invitation by guessing IDs, and an ordinary member cannot perform owner operations.
- Security tests verify no raw token or token hash appears in list, preview, logs, or persisted invitation output; the create response returns the raw token once in the configured client URL.
- Migration validation against a copy of the existing schema/data verifies every legacy `User.householdId` link backfills and earliest-created owner selection is deterministic.
- Run Prisma validation/generation, build, lint, unit tests, and database integration tests. Clearly identify checks blocked by unavailable PostgreSQL or environment configuration.

## Rollout And Compatibility

- Deploy additive schema and backfill before code that relies exclusively on membership rows.
- Keep legacy `User.householdId` populated or readable during the compatibility window only if a rolling deployment requires it; do not retain dual-write behavior after all app instances use memberships.
- Remove the legacy column only after confirming the deployed version no longer reads it and backfill validation passes.
- Existing access/refresh token behavior is unchanged. Household membership is always loaded/checked server-side; household role or selection is not trusted from a token claim.
- Update `docs/product/contracts/household-membership.md` if implementation reveals a necessary behavior change; clients must not infer behavior from implementation details.

## Acceptance Criteria

- An account can create a household and becomes its initial owner; household works with one member.
- Existing household links migrate to memberships without loss; earliest-created existing member (tie by user ID) is owner.
- One account can be current member of multiple households and can list/switch them client-side.
- A client-visible household UUID is stable and is used instead of the internal integer key.
- Owner/member permissions, self-leave, removal, role changes, and the last-owner invariant are enforced under concurrent requests.
- Invitations are owner-created, single-use, bearer links expiring after seven days, with raw token returned only at creation and only its hash stored.
- Owners can list pending invitation metadata and revoke invites later.
- Preview is unauthenticated and minimal; acceptance is authenticated, explicit, idempotent for an existing member, and atomic against concurrent acceptance.
- `CLIENT_APP_URL` is validated and used to construct invitation URLs; no request-origin-derived links are used.
- Former members cannot access current household data while historical attribution remains intact.
- API errors are stable and client-actionable, and client contract examples match the implemented routes/payloads.
